# 第二轮全应用性能优化

## 目标与实施范围

2026-10-06，在上一轮显示稳定性修正基础上，继续降低绘制、排版、分配和 LCD 更新开销。保持 tiny-flutter / tiny_gfx、ESP-IDF 6.0.2、显示方向、触摸及现有动画和采集频率。优化覆盖公共 renderer 和 Pad 输出；用量监控是本轮真实热点。

“极致优化”的验收依据是减少不必要的工作并保持画面和交互正确。主机性能数据与 P4 实机数据分开记录，不能用 Mac 的微秒结果承诺 P4 FPS。

## 实现

### 公共矢量与文字

- fill 借用已 flatten 的顶点；stroke 线段、三角和四点 join 使用内联顶点，减少每段临时堆分配。
- 多边形预计算 y 范围，只有会穿过当前采样行的形状才计算相交；保留半开边界、原顶点顺序、8 次抗锯齿、透明混合和渐变。
- 每个 `RenderText` 复用未变化的 `TextLayout`。失效条件包含完整文字、字号、换行、最大宽度、字体 Arc / provider 标志和活动字形包版本；新的最小宽高与高度约束每次重新计算。
- 保留旧 Font 引用，避免指针地址复用误判；同步字形包变更会重新测量内容文字。

### 监控实时组件与图表

- 今日总览的快速采样完成后，数字、费用、更新时间 / 错误状态和整个趋势卡片自行更新，不重复构建导航与未变化的额度 / 排行卡。
- 优化只适用于同一请求基线、同一页面 / 日期范围且静态卡片确实不变的结果。账号、模型、用户或昨日指标变化，配置、缺失数据、其他页面及完整刷新仍走正常 rebuild。
- 每 5 秒快速采样、每 60 秒完整看板刷新与手动刷新语义保留；失败不会伪装成新数据，stale / 部分更新提示立即刷新。
- 趋势卡片更换时先释放旧子树；标题、日期、费用、请求、选中位置、昨日数据及空曲线均跟随真实新数据。
- 原生 RGB565 图表区域与矢量共享已有 6 MiB 缓存预算，一个图表 namespace 只留当前版本。典型 540×71 绘图区约 76,680 bytes，加完整值 key；没有新增整帧缓存。
- key 包含真实绘图输入、颜色、范围和选中项；逐值比较，不用内容 hash 作为相等依据。几何、画布尺寸、平移和有效捕获范围同样检查。
- 命中不分配 key；失配先退旧版，再预留预算。预算 / 分配不足、超长 key、非整数边界及不支持的变换回退原矢量绘制。
- Token 千分位格式使用可容纳完整 u64 的 26 bytes 栈缓冲，避免动画每次格式化分配字符串。

### LCD 分带同步

- 每块 LCD 缓冲保留 32 个水平带的历史变更，而不是只累积一个大包围框。相邻且宽度相同的区域合并；相隔很远的数字和状态更新不复制中间未变化部分。
- 状态是固定大小结构，不分配堆，不新增全屏 buffer。600 行每带最多 19 行；三缓冲欠账仍分别累计。
- 低于整屏 75% 的真实累计变更面积走局部 CPU 复制，大面积仍用现有 PPA；0° / 180° 映射和 LCD padding / 容量校验保留。
- JPEG 返回 Pad、旧 epoch 的 BUILDING / READY 取消继续建立全帧恢复欠账。唯一 display owner、DMA completed / next 事件和封存 M2C 输出范围保持原合同。

### 可见更新与编译配置

- 实机中发现隐藏电池的毫伏级变化也会触发整树重建。电池继续每 2 秒采样 / 滤波；桌面按可见百分比更新，设备详情按显示的 0.01 V、百分比和充电状态更新，控制中心按百分比 / 充电状态更新。普通应用、熄屏和副屏不因隐藏电池变化重建；启动动画的桌面底图保留保守更新。
- 保存回执完整保留 Saved / Failed，仅可见“设置 → 存储”且状态变化时重绘；重复 Saved 不触发重建。真实 SessionWriter 成功读回和磁盘故障回执，以及 9 个应用中的电压抖动均有 Runtime 回归。
- `tiny_gfx` 与 `tiny-flutter` 的 release 包设置为 `opt-level=3`，优化逐像素、抗锯齿和分页循环。全局其余代码保持 `opt-level="s"`、LTO 和单 codegen unit。最终编译配置下重新跑 91 项 renderer release 测试，保留完整像素 oracle；应用仍在原 8 MiB 分区内。

### 细化诊断

- `p4desk_ui_stages` 分别记录 layout、paint、mount、builder、输出损伤像素、全屏 / opaque 帧；mount 包括创建 render object、首次 layout 与旧根释放，builder 单独计时；动画推进的提前 layout 另以 `advance_layout_us` 记录，避免漏掉动态卡片更换的开销。
- `total_max_us` 仅表示 `render_dirty` 的布局、绘制和输出，不是完整事件循环或端到端延迟。Rust 损伤像素是输出包围框，C 复制字节是实际分带面积；cache hits / misses 是累计数。拖动的 opaque 计数已修正为仅拖动帧。
- `p4desk_pad_copy` 添加 `regions_window`，与同窗口复制字节一起观察分带收益。
- 数值日志不包含画面、账号、便签、凭据或设备序列号。已有缓存同步和显示健康诊断保留。

## 主机验证

本地原始证据在 `.cache/system-display-audit/` 与 `.cache/extreme-performance/`，不进入 Git。

| 检查 | 结果 |
| --- | --- |
| Rust workspace | 404 项通过，50 个测试套件（含 doc-tests）；最终新增状态过滤与趋势回归另通过 Runtime 28 项、release renderer 91 项、live render 6 项 |
| 矢量像素 oracle | 1,440 组 stroke，32 组 compound fill，保留 cap / join、AA、渐变、裁剪、缩放、180° 与斜切 |
| 静态应用像素 | 11 个入口布局 / 绘制 hash 与改前一致 |

| C 显示路径 | Pad damage、pipeline、cache sync、pixel 输出与 HTTP 回归通过；包含 ASan / UBSan 的分带和三缓冲历史 |

最后三项是本轮合并后的综合收益，不单独归因于某个组件；属于合成主机缓存命中场景，不代表真实数据变化时完全无需重绘。相同二进制交替旧 / 新 stroke 测量中，24 / 240 点 Miter / Bevel 耗时下降约 24–30%，Round 约 5–7%；两点 Round 有约 +6% 的微秒波动，不宣称所有短路径变快。

为隔离实时组件更新的收益，新增 `cargo run --release -p app-launcher --example usage-live-probe`：同一套当前 renderer / cache，双方跑相同预热和 10 次虚构的 5 秒采样，包含曲线改变 / 不变、数字、费用和状态变化。最终像素 0 差异；显式 rebuild 路径的 10 次 mount / 全屏帧减少为 0，分配 9,621→2,404 次，临时 live 峰值增量 37,825→6,677 bytes。该工具不用网络、TF 或真实凭据。阶段计时按最终日志记录，不能将提前 layout 排除后得到的 draw 解释为全部 CPU 开销。

独立编译配置对照使用全局 s + LTO，仅变更两个渲染包 s→3：170 个场景对、290 个阶段像素 hash 和 45 个 stroke hash 均一致；保留缓存量及命中计数相同。合成主机中，冷桌面中位耗时改善约 12–19%，外观页约 8–21%，换主题约 13–25%。短的两点 Round stroke 增加约 0.7 us；热态部分缓存路径有微秒波动。没有宣称每条路径都变快。

分带测试中，屏幕上下两块变更的包围框达数十万像素，实际复制两区合计仅 1,920 像素；随后第三块变更仍保留其他缓冲的 2,320 像素历史欠账，完整独立像素参考一致。

## 构建、刷机与目标验证

构建、刷写、目标数值及视觉验收分开记录于 [本轮验收记录](acceptance-extreme-performance.json)。用户上一轮的稳定反馈见 [显示与内存验收](acceptance-system-display-memory.json)，不代替这一版的实机观察。

### 首次绘制的边界

中间版的交互窗口曾记录 `draw_max_us=4,170,790`，同时大量矢量缓存首次生成；用户随后确认操作顺畅、画面稳定。合成定位表明：分页缓存首次在黑底 / 白底采样两页后，静止桌面仍由原组件绘制，这会产生冷绘制峰值。速度编译降低循环成本，保留该生命周期；不能仅凭热态平均值宣称冷峰完全消除。最终版采样的监控绘制峰值单列如下；没有覆盖桌面首次更换主题，不能把这段较安静窗口当作冷峰已消除的证据。

### 最终版数值记录

最终应用固件 6,504,176 bytes，SHA-256 `fa3ed3ab36f9945f0374c4664dcb99d94aed9bfb7ffa94915a1f1e46691a388c`；8 MiB 应用分区内完成链接，274 个源码文件与构建时 hash 一致。ESP-IDF 6.0.2 / nightly-2026-09-27 构建成功，bootloader、分区表与应用三处刷写 hash 校验通过，未擦除 NVS / TF。

连续采样约 11 分钟，最后一次诊断 uptime 631 秒：无新增重启、panic / assert 或分配失败；内部 heap 最低 65,939 bytes，PSRAM 最低 17,865,712 bytes。bridge underrun、M2C、缓存同步、PPA 错误 / 超时均为 0。DSI host 保留一次启动期 `status0=0x100000` 记录，没有把它抹掉或宣称全部 host 标志为零。

请求完成 131 次，其中 130 次成功，开机尚未联网的一次 Offline；之后启动间隔中位 5,001 ms，范围 4,981–5,021 ms。begin 日志在第 24 次之后节流，未打印的启动时间由完成时间减耗时推算，不伪造 full / headline 类型。保存检查点 12 次成功、0 次失败。

按至少 4 次请求、约 5 秒间隔且未记录拖动的数值筛选，得到 20 个监控前台代理窗口、511 帧；不能排除点击或其他活动。按帧数加权 draw 约 6.07 ms，输出约 2.38 ms，窗口 draw 峰值最高 75.86 ms；每 30 秒窗口 mount 1–2 次。预推进 layout 506 次、合计 352.56 ms，另计 mount / builder；这些值不构成完整事件循环延迟或 FPS / P95。

与中间版相近 uptime 且满足相同筛选条件的 18 个窗口对应：最终版 27 次 mount，中间版 101 次，最终窗口内 108 次请求。说明每个 5 秒 headline 必定挂载的系统性路径已消除；两轮不具有相同数据与操作，不给出严格 A/B 百分比，也不单独归因于编译配置。

采样窗口累计复制 12,910,878 bytes；相同已呈现次数若全部复制完整帧，理论参考为 663,552,000 bytes。这个差值说明局部提交生效，不是旧固件同负载下降率。

用户已确认中间版“操作顺畅，画面和点击正常”“更新正常，画面稳定”。最终版补充的状态过滤和速度编译已完成目标构建、刷写和上述数值采集；首次主题生成的额外视觉问题尚未收到答复，验收记录明确保留该边界。本轮没有重新测量 USB JPEG 副屏帧率或 BLE 连接业务。
