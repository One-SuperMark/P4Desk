# 全应用显示、内存与性能检查

## 2026-10-06 问题范围

实机仍偶发短暂闪绿、整幅画面水平错位，随后继续停留在原页面。用户确认不操作时也会出现。此前的显示 QoS、缓存安全 ISR 与 C2M 分块版本没有完成这一问题的验收，因此这次同时检查所有应用共用的 Rust 渲染、缓存、Pad 输出、PPA／JPEG 和 LCD 三缓冲路径。

保留 tiny-flutter／tiny_gfx、ESP-IDF 6.0.2、唯一 display owner，以及现有显示和触摸方向。问题原因不能仅凭症状认定为内存不足；以下分别记录发现、修正和验证边界。

## 本轮修正

### Rust 缓存与图像边界

- 矢量缓存的 6 MiB 像素预算同时计算已保留数据和正在生成的前后像素快照。生成前先预留、淘汰，嵌套生成共用同一预算；失败时直接绘制原矢量。
- 分页缓存的 4 MiB 预算包含黑白捕获缓冲、RGB565、透明度和像素段。更换主题前释放旧分页缓存，按容量计算中间峰值；无法缓存时使用原组件绘制。
- 遮罩、图像和 Pixmap 检查尺寸乘法及实际切片长度，拒绝溢出／不足的数据。
- 字体及字形包缓存在提交时再次检查同一 key，避免并发未命中重复计入缓存字节。

这些预算针对各自的像素缓存，不代表整机内存上限。控件、字形、LCD 缓冲、网络栈等仍另外占用内存。

### Pad 局部输出

- Rust 仍同步借用 RGB565 区域。C 在 Pad 锁内逐行比较新旧像素，只复制实际变化的首尾范围。
- 三块 LCD 缓冲分别累计尚未同步的矩形。轮到某一块使用时，将它缺少的历史变化一并补齐，不能只复制最后一次变化。
- 小于屏幕 75% 的更新走 CPU 局部复制；大面积过渡继续使用 PPA 全帧复制／旋转。
- 提交始终使用 framebuffer 完整基址，DPI 仍扫描 1024×600。局部 y 范围只缩小新内容的整行 C2M 写回。
- JPEG → Pad 与旧 epoch 的 BUILDING／READY 取消均重新建立完整恢复请求。恢复标志与模式／epoch 一起发布，防止副屏残留或错误清掉新模式的欠账。

该路径不增加全屏缓冲。LCD 所有权仍由真实 DMA completed／next 事件转移，不以等待固定时间替代。

### Cache 同步和诊断

- SDK 自带的 chunk 配置只涵盖 C2M。PPA 与 JPEG 的数据 M2C 请求仍可能一次处理约 1.2 MiB 输出。
- 项目使用链接包装 `--wrap=esp_cache_msync`，在启动时登记并封存三块 LCD allocation 和 JPEG scratch 的真实范围。符合条件的 task 数据 M2C 请求按 32 KiB 分块，保留 flags 和 SDK 错误返回。
- ISR、C2M、instruction sync、未对齐、未登记／跨范围和非法请求继续调用原 SDK。包装入口、原 SDK 与 ISR 查询必须在最终 ELF 中核对 IRAM 链接。
- 包装不改变 SDK 源码，也不替代输出缓冲独占要求。SDK ISR 路径不进入闪存 helper。
- 移除运行时诊断和 HTTP 日志中的 `heap_caps_get_largest_free_block`。该 API 在 critical section 中遍历堆，改为读取空闲量／历史最小空闲量。
- 启用轻量堆边界保护 `CONFIG_HEAP_POISONING_LIGHT`。分配失败回调只更新内部 RAM 的原子计数，不分配、打印或遍历堆。

`max_chunk_us` 是单块 SDK 调用的经过时间，包含抢占，不能解释为精确关中断时长。

## 实机证据

本轮构建、刷写、连续运行数值与用户视觉反馈见 [全应用验收记录](acceptance-system-display-memory.json)。历史短时无错误日志不能替代本轮“空闲也闪屏”的视觉验收。

本轮已使用最终源码重新构建并刷写，bootloader／分区表／应用三段 hash 校验通过；固件大小 6,463,680 bytes，SHA256 为 `355bba05fcc848d420a03298462b8f4e5fd1d321dab0b9fb820ca2bcadc2867c`。UART 连续记录 660 秒，共 21 个诊断样本，最后诊断 uptime 为 632 秒：

- 分配失败、堆保护／panic、LCD bridge 欠载、PPA 错误／超时、C2M／M2C 错误均为 0。
- 最小内部空闲量 55,915 bytes，最小 PSRAM 空闲量 17,247,564 bytes；末次 PSRAM 空闲量 18,258,716 bytes。
- 244 次更新：193 次局部、51 次全帧；另跳过 85 次无变化准备。统计窗口内复制 69,260,298 bytes；同次数整帧复制基线 299,827,200 bytes，减少约 76.9%。这是像素复制量统计。
- 51 个 M2C 输出请求拆成 1,938 块，单块最长经过时间 114 us。DMA 边界最长间隔 16,673 us，超过 25 ms 次数为 0，事件队列峰值 2。
- 20 轮在线取数成功、72 个 HTTP 请求全部 200；12 次 checkpoint 成功、失败为 0。
- 首轮 DSI Host 状态样本包含一次 `ST0=0x100000`／`ST1=0`，`first_us=last_us=461055`；9,557 次累计采样中后续计数未增加。不将它表述为全部 DSI 错误为 0。
- 用户反馈“目前画面稳定，没有再闪绿或错位”。这是本轮观察反馈；没有以 11 分钟记录宣称全天无闪屏，也没有重新做 USB 真副屏实机压测。

诊断字段：

- `p4desk_diag`：内部 RAM／PSRAM 空闲量与历史最小量、分配失败次数和最后失败大小／caps。
- `p4desk_pad_copy`：局部／全帧／无变化次数，以及每 30 秒实际复制字节数。
- `p4desk_m2c`：符合条件的请求、实际分块、SDK 错误和单块最长经过时间。
- `p4desk_dsi_host`／`board_p4` 的 `display underruns`：主机状态、桥接欠载与只由 display owner 采样的错误统计。
- `p4desk_display_health`：DMA 边界间隔、事件队列峰值与 C2M／PPA 统计。

当前持久化写入仍可能造成 Flash 暂停；异步保存不能保证完全没有总线或 cache 暂停。没有在未确认 Flash 支持的情况下开启 auto-suspend。内存失败计数为 0 和堆保护没有报错，仅表示观察期没有检测到这些异常，不证明不存在所有越界或显示硬件异常。

## 记录期间发现的剩余绘制开销

监控页部分低频窗口的实机 `draw_avg_us` 约 193 ms，完整重绘最大约 512 ms，output 约 18 ms。此 draw 只包含 `render_dirty` 中的 layout／paint，不包含此前 builder／`set_root` 的首次 layout。

只读合成热点分解表明：24／31 点真实监控树的热 paint 中，趋势图区占约 89%／91%；数字局部 opaque 更新 40／40 帧成功，局部 App draw_avg 为 20 us。导航玻璃热缓存的耗时很低。这里的比例与微秒是 Mac host 结果，不能直接当作上述 P4 耗时分解。

代码路径确认，快速采样完成时仍通过 `state.changed()` → revision → rebuild 触发完整绘制；曲线每次 paint 重新计算几何、flatten、圆头／圆接点与抗锯齿。后续可优先复用未变化的图表像素／几何，并将费用、更新时间局部更新。此次未据主机热点修改监控数据更新语义或整树布局契约。
